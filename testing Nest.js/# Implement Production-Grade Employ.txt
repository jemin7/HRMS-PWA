# Implement Production-Grade Employee Background Location Tracking for the Attendance System

## Role

Act as a senior full-stack engineer working inside an existing attendance application.

You are implementing a feature that was already prototyped and tested successfully in a separate test project. Use the behavioral design described below as the **source of truth**, but **do not copy the test project blindly**.

Before changing anything:

1. Inspect the main project's existing architecture.
2. Identify the current frontend framework, navigation structure, authentication mechanism, attendance/punch flow, local database layer, backend framework, ORM, PostgreSQL schema, API conventions, error handling, environment configuration, background-task infrastructure, and deployment configuration.
3. Reuse existing abstractions and coding conventions wherever possible.
4. Integrate this feature into the existing architecture instead of creating parallel or duplicate systems.
5. Do not break the existing attendance Punch In/Punch Out, offline synchronization, authentication, or database behavior.

The final implementation must be production-ready.

---

# Feature Requirement

While an employee is punched in:

- Start background location tracking.
- Capture approximately one location every 10 minutes.
- Store latitude and longitude.
- Store the capture timestamp.
- Associate every location with the specific Punch In attendance session.
- Always save the location locally first.
- If internet is unavailable, keep the location in SQLite/local storage with `PENDING` status.
- When internet becomes available, automatically upload pending locations.
- If upload fails, retain the location locally and retry later.
- Prevent duplicate server records using an idempotent client-generated location ID.
- Continue tracking while the app is backgrounded.
- Stop tracking immediately when the employee punches out.
- Stop tracking automatically after 9 hours from Punch In.
- If the app returns to the foreground while the employee is still punched in, recover/restart tracking when appropriate.
- Detect when Android Location Services are disabled while an employee is punched in and notify the employee.
- Keep the notification logic from repeatedly spamming the employee.
- Do not continue collecting locations after Punch Out or after the 9-hour limit.
- Existing attendance synchronization must continue to work unchanged.

The 10-minute interval must be treated as **approximately 10 minutes**, not an exact guarantee. Android may defer or batch background location callbacks because of OS, battery, and device-vendor behavior.

---

Do **not** use a generic background task scheduler as the mechanism for the 10-minute location interval if the platform's scheduler cannot meet the requirement.

- `expo-task-manager`

The background task receives Android-delivered location updates.

If the main project is not Expo/React Native, implement the equivalent native background location mechanism for that platform rather than copying Expo-specific files.

# 9. Backend Sync Logic

Equivalent backend behavior:

```ts
async syncLocation(dto: SyncLocationDto) {
  const user = await this.prisma.user.findUnique({
    where: {
      id: dto.userId,
    },
  });

  if (!user) {
    throw new NotFoundException(
      `User with ID ${dto.userId} not found.`,
    );
  }

  const existing =
    await this.prisma.attendanceLocation.findUnique({
      where: {
        clientLocationId: dto.clientLocationId,
      },
    });

  if (existing) {
    return {
      success: true,
      duplicated: true,
      location: existing,
    };
  }

  const location =
    await this.prisma.attendanceLocation.create({
      data: {
        clientLocationId: dto.clientLocationId,
        sessionEventId: dto.sessionEventId,
        userId: dto.userId,
        latitude: dto.latitude,
        longitude: dto.longitude,
        capturedAt: this.wallClockToDate(dto.capturedAt),
      },
    });

  return {
    success: true,
    duplicated: false,
    location,
  };
}
```

Production implementation must preserve the same idempotent semantics.

If two requests with the same `clientLocationId` arrive concurrently, the database unique constraint must protect against duplicates.

Handle the resulting unique-constraint race condition cleanly and return the existing record or equivalent success response.

# 10. Timestamp Contract

The prototype uses a trusted server-time system.

The location capture timestamp format is:

```text
YYYY-MM-DD HH:mm:ss.SSS
```

Example:

```text
2026-10-07 13:03:19.123
```

Do not send:

```text
2026-10-07 13:03:19.undefined
```

Do not depend on `Intl.DateTimeFormat(... fractionalSecondDigits ...)` producing a `fractionalSecond` part on every Android/Hermes runtime.

The tested implementation fixed this by manually constructing the timestamp using numeric UTC components plus the IST offset.

If the main project already has a trusted server-time abstraction, reuse it.

If the main project requires trusted timestamps, preserve the existing behavior:

```text
Server UTC time
+
monotonic elapsed time
=
trusted current time
```

The mobile wall-clock timestamp must not become the source of truth merely because the feature is running in the background.

# 12. Local Queue Behavior

Every captured location must follow this flow:

```text
Location received
        ↓
Save to SQLite
        ↓
PENDING
        ↓
Attempt network upload
        ↓
Success → SYNCED
Failure → PENDING
```

Always save locally first, even when internet is currently available.

This prevents loss when:

- network disappears
- the upload request fails
- the server is temporarily unavailable
- the process is interrupted
- Android kills/restarts application execution
- the connection times out

# 15. Location Sync Service

Create a dedicated location synchronization service.

Do not mix location data into the attendance sync logic unless the existing architecture already has a generalized offline queue abstraction that should be reused.

Required behavior:

1. prevent concurrent location sync processes
2. check network connectivity
3. recover `SYNCING` records to `PENDING`
4. load pending locations ordered by ID
5. mark each record `SYNCING`
6. POST to `/attendance/location/sync`
7. mark success as `SYNCED`
8. on failure increment attempts and restore `PENDING`
9. continue processing the next record
10. report remaining count

Example payload:

```json
{
  "clientLocationId": "1791380000000-abc123",
  "sessionEventId": "1791379999999-punchin",
  "latitude": 19.2032612,
  "longitude": 72.8350578,
  "capturedAt": "2026-10-07 13:03:19.123"
}
```

Use an upload timeout.

Do not delete failed records.

# 21. 9-Hour Automatic Stop

The tracking session must automatically stop after:

```text
9 * 60 * 60 * 1000
```

Use a monotonic clock or another reliable elapsed-time mechanism rather than trusting the phone's wall-clock time.

Store persistent tracking state similar to:

```ts
type TrackingState = {
  active: boolean;
  userId: number;
  sessionEventId: string;
  startedAtWallMs: number;
  startedAtMonotonicMs: number;
  bootCount: number;
};
```

When the background task executes:

1. load the state
2. verify tracking is still active
3. verify boot count
4. calculate elapsed monotonic time
5. if elapsed >= 9 hours:
   - stop location updates
   - clear tracking state
   - do not save further locations

# 22. Device Reboot / Monotonic Clock Handling

The tested implementation treats a boot-count change as an invalid continuation state.

If:

```text
currentBootCount !== savedBootCount
```

then:

```text
stop tracking
clear tracking state
require a new valid attendance/session state
```

Do not reconstruct elapsed time across a reboot using an untrusted phone wall clock.

If the main project has a stronger trusted-time/session recovery mechanism, use it, but do not silently weaken time integrity.

# 23. Tracking Recovery

The app must recover an active tracking session when it returns to the foreground.

On application initialization and AppState transition back to `active`:

```text
Is employee still punched in?
        ↓
Is location tracking running?
        ├── yes → leave it running
        └── no → recover/restart it
```

Before restarting, verify:

- tracking state exists
- session is still active
- background permission is granted
- boot count is unchanged
- 9-hour limit has not been reached

If 9 hours have elapsed, stop and clear tracking state.

If permission is missing, stop tracking and show the appropriate user-facing state.

If Location Services are disabled:

- do not silently continue as if tracking were healthy
- trigger a local notification
- prevent starting a new tracking session while location services are disabled
- on app foreground, re-check the state
- when Location Services are restored, clear the warning state and allow/recover tracking

Do not spam repeated notifications.

Persist a flag such as:

```text

```

to prevent repeated identical notifications until the condition changes.

Important platform limitation:

Do not claim the app can guarantee an instantaneous notification the exact moment GPS/Location Services are disabled while the app is fully backgrounded. Android may stop delivering location callbacks. The implementation must use both:

1. background-task detection

# 33. Existing Stale Punch Out / Duplicate Behavior

The prototype exposed one important edge case:

An old pending Punch Out may return:

```http
409
This attendance record already has a Punch Out.
```

This can happen if the server already processed the Punch Out but the client never marked the local event as synced.

Production implementation should make attendance synchronization idempotent as well.

For a known duplicate/already-completed server state:

- detect the server response as an already-processed event
- mark the local event `SYNCED`
- do not leave it permanently `PENDING`

Do not weaken actual duplicate protection.

# Final Implementation Principle

Use the existing main project's architecture as the primary source of truth.

The previously working prototype demonstrates the correct **behavioral design**:

```text
Punch In
    ↓
Create attendance session
    ↓
Start background location
    ↓
Location received
    ↓
SQLite FIRST
    ↓
PENDING
    ↓
Internet available
    ↓
Sync API
    ↓
PostgreSQL
    ↓
SYNCED

Punch Out OR 9 hours
    ↓
Stop tracking
```

Adapt that design to the main application's:

- authentication
- API client
- database layer
- navigation
- attendance model
- synchronization framework
- logging
- deployment system
- coding conventions

Do not copy prototype shortcuts such as hardcoded `USER_ID = 1`, duplicated API URL constants, duplicate network listeners, or test-specific IDs.

The implementation should behave exactly as described above while fitting naturally into the main project's existing architecture and preserving all existing functionality.
